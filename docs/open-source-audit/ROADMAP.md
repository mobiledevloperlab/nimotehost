# Minimal roadmap before open-source release

This roadmap is an audit result, not authorization to implement changes. Priorities, findings and evidence are recorded in [AUDIT_REPORT.md](AUDIT_REPORT.md), [LICENSE_COMPLIANCE.md](LICENSE_COMPLIANCE.md), [SECURITY_PRIVACY.md](SECURITY_PRIVACY.md) and [EXTENSIBILITY.md](EXTENSIBILITY.md). No production implementation, dependencies, configuration or licenses were changed in this task. The additional user request authorized language corrections in existing documentation only.

## Release gates: six work groups

No confirmed P0 authorization bypass or public secret exposure was established. Do not convert an unverified assumption into a security-vulnerability count. The following six groups distinguish one concrete packaging fix, two owner confirmation groups, and three acceptance/validation groups (including affected desktop dependency triage).

| Gate / priority / conclusion | Actual behavior and code evidence | Smallest required action and completion evidence | Existing NimoteCode user impact |
| --- | --- | --- | --- |

For source publication, G2/G3 are the direct rights/privacy gates. Close or clearly qualify G4's compatibility claims. G1 applies to distributed GUI binaries; G5/G6 apply to the support/security claims made for release artifacts. Do not advertise an all-platform production acceptance result solely because source can be built. The present workflow publishes both CLI and GUI together on a version tag (`ci.yml:234–250`), so its combined release needs the applicable binary gates as well.

### What counts as “must fix a security issue” here?

SEC-01 requires credential handling if the local values are real. REL-03 requires resolving or explicitly justifying desktop known-vulnerability findings before binary release; static decoder reachability alone does not establish a remote exploit. It does not justify rewriting history without evidence of committed leakage. SEC-02/COMP-01 require truthful execution/approval boundaries and client acceptance; a failed check may reveal a defect requiring a targeted fix. The current audit did not establish an unauthenticated control path, device-to-owner route bypass, exposed public listener or universal approval bypass. Same-user plugins executing same-user code is the disclosed design.

No broad sandbox, changed SSH server configuration, automatic token rotation, lower default timeouts or removed command execution is required merely to make source public. Such changes could disrupt existing users without addressing an established defect.

| ARCH-01 / P2 | Process-global community resolver and large Host state package (`plugins.go:198–245`, `manager.go:35–65`). | Pass resolver explicitly only as concrete needs arise; keep core session/approval lifecycle shared. | Internal maintenance only; no package-wide rewrite. |
| ARCH-02 / P2 | Plugin recovery counts three failures over lifetime (`plugins/runtime.go:688–762`). | Document policy or reset after a measured healthy interval; retain bounded recovery and no operation replay. | More predictable plugin availability. |
| REL-02 / P2 | SHA256 checksums without publisher signatures, movable Action tags (`tools/build/archive.go:85–92`, `ci.yml`). | Pin release actions; consider simple provenance and platform signing/notarization appropriate to release channel. | Easier trust verification; not an auto-update project. |
| DOC-01 / P2 / Completed | English docs contained Chinese prose; Chinese docs contained English paragraphs/headings and obsolete section fragments. | Corrected eleven root Markdown documents: six English and five Chinese. Preserved technical identifiers, upstream license text and translation assets. | Documentation only. |

Avoid making every recommendation a release blocker. First satisfy actual redistribution, privacy and compatibility evidence; then take small improvements when they solve an observed maintenance problem.

## Explicitly unnecessary now

| Design to avoid | Existing mechanism that already meets the need | Why defer |
| --- | --- | --- |
| Dynamic Go/shared-library plugins and hot loading | Process SDK/HCP/ACP (`pkg/pluginsdk`, `internal/plugins`). | Adds ABI/toolchain/platform coupling and in-process crash/security exposure. |
| Marketplace, dependency solver, auto-install/update ecosystem | Explicit owner-reviewed local package and optional existing catalog. | Adds publisher trust, dependency resolution, rollback and continual moderation obligations. Freeze the present catalog scope. |
| General workflow DSL, task scheduler, hook framework | Existing command+argv task/terminal execution and specific workflows. | Simple script recipes cover customization without a language/runtime to maintain. |
| Universal Agent protocol and raw RPC passthrough | Narrow native adapter descriptors, shared transport/lifecycle and provider-specific projections. | Different approval/history/attachment semantics should not be hidden by an abstraction or arbitrary privileged forwarding. |
| Claiming a portable sandbox from grants/UID metadata | OS-account boundary plus optional existing native constraints. | Permission labels do not enforce file/network restrictions; optional OS isolation should remain honest and scoped. |
| Downloaded native/Flutter plugin UI or unrestricted WebView | Existing bounded schema/UI vocabulary with client fallback. | Adds arbitrary code/content origin risks and a second application platform. |
| New public HTTP listener, cloud account system or relay | Existing externally authenticated SSH plus loopback API. | Adds an exposed transport/identity service unrelated to source transparency and low maintenance. |
| Broad package extraction, new repositories and universal SDK export | Existing internal packages and small public protocol SDK. | Freezes unstable internals and increases coordination cost before there is a concrete consumer. |

## Completion and tracking

Count: **six release work groups**, with local portions of G3/G5/G6 already evidenced. This is one established desktop packaging correction, two owner confirmation groups and three acceptance groups including desktop dependency remediation/triage, rather than an estimate of six code changes or six vulnerabilities. Native/mobile/rights work cannot be honestly assigned completion dates from this Host-only checkout.

Keep the release record small: baseline commit, artifact hashes, included notices, rights confirmation, no-value secret-scan scope, intended client versions and platform check outcomes. Reopen only the groups affected by subsequent implementation/dependency/asset changes. The objective is a transparent and customizable Host with stable NimoteCode contracts, using the existing architecture.
